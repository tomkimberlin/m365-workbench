# Quality review — 2026-09-22

Scope: recovery-panel layout, inventory/filter responsiveness, empty/error states, and recovery-cache lifetime. This review used local source inspection, real WPF layout, and synthetic offline fixtures. No live recovery values were requested or production screenshots published.

## Corrections

- Both recovery-status rows now give their text a finite width, allowing countdowns and cleanup messages to wrap. The previous horizontal container measured its children with unlimited width, defeating text wrapping. Long administrator and volume labels also wrap; unusually long sign-in labels are bounded with the full value available as a tooltip.
- Inventory filtering snapshots the search and filter controls once per refresh instead of once per row. Inventory totals are counted in the collection-building pass, and selection restoration avoids an extra materialized copy of the filtered view.
- A successful zero-device inventory is accepted and displays the normal empty state. Previously, mandatory array-parameter validation rejected an empty collection before the UI could handle it.
- Cached LAPS and BitLocker actions now compare their deadlines against the same elapsed-time clock used to create and expire them. Windows clock adjustments cannot affect cache reuse decisions.
- Authentication failures and Graph 401 responses revoke local verification, hide cached/displayed secrets, and disable recovery actions until sign-in succeeds. Other request errors retain the existing retry behavior.

## Verification

- All 188 offline checks passed locally after the first pass.
- The complete offline suite includes actual WPF layout assertions for both recovery panels at 1100, 1280, and 1600 pixel logical widths, with enlarged status text and countdown, cleared, and busy-cleanup messages.
- Actual production action functions are tested against simulated clocks that differ from wall time. The production operation-completion path is exercised with a synthetic Graph 401 response.
- Inventory tests cover Entra-only disappearing during refresh, independent no-match searches, a completely empty inventory, recovery from empty, 5,000-row search/count correctness, and retained selection.
- Synthetic LAPS and BitLocker clipboard-status previews were rendered and visually checked. Preview state does not retrieve secrets or write to the clipboard.
- One same-machine 5,000-row comparison measured inventory binding/filtering at 287 ms before versus 103 ms after, and search at 78 ms before versus 41 ms after. These are local smoke measurements, not network timings or performance guarantees; timing is reported but not used as a flaky pass/fail threshold.

## Limits

This is not a live-tenant permission, authentication-policy, or real-device recovery test. It does not establish a fix for previously observed native PowerShell/runtime process crashes. The security and platform limitations recorded in the [earlier audit](AUDIT-2026-09-05.md#remaining-limits) still apply. Local verification settings are not changed by this update.

## Follow-up — build 2026.09.28

- Refresh now provides a Cancel action. Cancellation is asynchronous: the UI continues processing its timers while the worker stops. Previous inventory and sign-in survive cancellation and transient request failures; failure messages identify when older inventory is still displayed. Canceling before a completed result reaches the UI still discards that result. Cancellation is cooperative, not a guarantee of immediate termination of an unresponsive native/network call.
- Worker initialization and invocation-start failures use the normal UI error path instead of escaping an event handler. Broken workers can be recreated on retry. Unexpected result kinds fail closed, and completed error/progress streams are released.
- Sort order, column arrows, and the selected BitLocker key survive refresh when still applicable. Devices without a valid Entra ID use their Intune ID for selection restoration.
- Switching devices, tabs, or key records, or pressing Escape, dismisses pending recovery intent. Late secret responses are released without copying/revealing them; late local or Microsoft verification cannot revive the dismissed action. This does not revoke an otherwise valid verification grant or change the configured verification mode.
- Timer- and session-driven clipboard cleanup use one nonblocking open attempt. Contention preserves ownership for the next scheduled attempt, without a repeated sleep loop on the UI thread. Expired sign-in also requests immediate protected-clipboard cleanup.
- Recovery details show a short key ID beside the volume name, with the full ID on hover. Picker items expose the full ID and support ID-prefix keyboard selection. No additional Graph calls or permissions are needed.
- Hosted Windows testing caught a font-dependent wrap of the longer volume label that could push Copy below the initial viewport. The volume label now stays on one line with ellipsis and a full-text tooltip, preserving the primary action's space across font environments.
- Long footer messages remain inside their available width and expose their full text on hover. HTTP status codes take priority over incidental error-message words, with distinct guidance for service outages, throttling, timeouts, wrong account/tenant, and missing permissions.

Follow-up verification includes actual asynchronous worker execution, startup/broken-worker injection, successful retry, cancellation/completion races, twenty alternating refresh/cancel cycles, delayed secret/verification results, selection preservation, and nonblocking clipboard shims. Real WPF checks cover long footer messages and the default-size BitLocker Copy button for all three known volume labels. Synthetic clipboard and refresh-in-progress screens were rendered for visual review.

Final verification on September 28: all 234 offline checks passed on both PowerShell 7.6.5 and the installed Store PowerShell 7.6.6. The installed shortcut was checked, and local settings were preserved unchanged.

Implementation reference: [PowerShell asynchronous stop](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.powershell.beginstop?view=powershellsdk-7.4.0). The app supplies no scriptblock callback on a background thread and waits for stop completion through its existing UI polling mechanism.
